# Job Apply — Changelog

Append a dated entry for every behavioural change. Say what changed and why. Older entries stay; correct them with a newer entry instead of deleting them.

## 2026-11-11

- **90-second same-site pacing added at the user's request.** After each verified application, `job-apply` waits at least 90 seconds before opening or starting the next job on that site. The site reference's shorter pacing no longer overrides it. Different sites are unaffected, but they still run sequentially.
- **Learning rule made explicit.** Any new finding (selector, question type, login step, rate limit, external-ATS pattern, status phrase) must be written into the corresponding `references/` file before the run ends, and a behavioural change goes into this changelog.
- **Split into three skills at the user's request:** `job-find` harvests and queues `Drafted` rows, `job-apply` submits the drafted queue, and `job-update` syncs statuses from Gmail. The three live side by side under `~/Desktop/skills/job skills/`.
- `job-apply` now reads its queue from the site page's `Drafted` rows instead of searching the sites. Searching moved to `job-find`.
- Answer style is now a first-class reference, `references/answer-rules.md`: 2 to 3 human sentences, no `--`, em dash, en dash, bullets, emoji, or markdown, and never exceeding a stated character or word limit.
- Resume bundle moved into `job-find/resume/` (`resume.md` and `mukul_pretham_resume_v5.pdf`). `job-apply` references it relatively and keeps `resume.md` locally as a fallback.
- Notion writes are status-only: `Drafted` to `Applied`, with the verified IST timestamp. The full row text is read fresh before every update.
- `browser-control` is documented as `browse` on this machine, with `tools["browser-control"]` as the alternative name in other harnesses.

## 2026-11-08

- **Cutshort added as a covered site.** New `references/cutshort.md` maps the candidate UI (everything under `/profile/`, top-level paths 404), the pending/questionnaire queue at `?i=all&stage=awaiting`, the custom-radio divs whose selected state sits on the child indicator, the irreversible submit confirm, and the thread composer. Registered in the SKILL.md table, canonical names and aliases.
- **Empty Messages tab is not "no recruiter activity".** At Cutshort the Messages tab counts unread conversation replies only; screening questionnaires live on the applications side. Recorded so an empty Messages view is never reported as silence.
- **Message tone rule promoted to SKILL.md (user directive).** Recruiter messages are plain human cold text: no em dashes, no `--` separators, no bullets. Two or three sentences, greet by first name, offer a call.
- **Questionnaire pay bands are often only in the legend.** `This job offers around ...` is the sole pay signal on many threads, so the reference requires reading it before answering the pay question and sending sub-floor bands back to the user instead of answering yes.

- `references/hiringcafe.md` §4.0 simplified: the pre-batch applied set is one fetch of the single `Hiring Cafe` page, not a sweep of every date page. `Run Notes` and `Hyderabad Outreach` both still pollute a `notion-search` for the site name.
- **Candidate facts filled from a verbal interview (same day).** `candidate-profile.md` Education and Identity gained Class X **2020**, Intermediate **2023**, Class XII location (Madhapur) and a partial home address. Two figures conflict with the resume (XII **92% spoken vs 91%** on the resume; X **90% spoken vs CGPA 9.4/10**) and were recorded as conflicts, not overwrites — the resume still governs until he confirms. The "open facts" table now labels each gap still-open / probably-resolved / half-resolved so the next run knows exactly what to ask. PIN logged as incomplete on purpose: he said "5003" and Hyderabad PINs are 6 digits.

Added a harness note: a lighter harness browser tool (Hermes `browser_exec`/`browser_cdp` over CDP, no extension) may be used for read-only recon only — listing pages, reading a JD, taking notes. Rationale: in Hermes the CDP path runs a *different* Chrome profile with different logins, so using it to submit would silently lose the user's sessions. ## 2026-11-05

- **Parallel three-site run at the user's request (30 requested; 24 verified in the first pass — Indeed 10, Wellfound 10, Hiring Cafe 4 — then a continuation agent dispatched for the rest).** New `SKILL.md` section **"Parallel multi-site runs (explicit user override)"** records the five setup steps that made it work: pre-create the Notion date + site pages in the parent, freeze one shared prior-applied dataset, give each agent its own named browser-control session driven by `browser-control execute --session ... --json --file`, hand each agent a site brief file instead of a chat message, and require a per-site `work-<site>.jsonl` so the parent can audit afterwards. - Added the **browser-control CLI path** as the supported way for delegated agents to drive tabs. Subagents reliably have a terminal; they do not reliably have the browser MCP tools, and `session_use` does not persist across processes. `browser-control execute --session <id> --json --file <script>` returns a clean `{ok, value, ...}` envelope and keeps each agent in its own tab.

## 2026-11-10

- **Wellfound location gates split in two.** The runbook now distinguishes the modal-level "does not support the locations on your profile" gate, which the candidate can clear with the `I can relocate to…` radio plus the location combobox, from the employer-level "not accepting applications from your current location" gate, which requires a profile edit and must be parked. Recorded because 8 of 28 applications today only existed after clearing the soft gate, and 7 strong roles died on the hard one.
- **react-select commit procedure documented** for the location field: label click, programmatic focus (`input[id*="locationId-input"]`), keyboard type, ArrowDown, Enter, then assert the hidden `qualification.location.locationId` is populated and the submit button is enabled. Includes the city-name mismatches (`Gurgaon` vs `Gurugram`, `Bengaluru` vs `Bangalore`).
- **`Improve your odds (N+ years)` reinterpreted.** It is an informational warning that also fires at `1+ years`; only `2+` and above is a hard skip. An earlier same-day attempt cancelled four 1+ roles because of it, and all four were resubmitted or reclassified afterwards.
- **Batch failure handling.** Each job in a batch now needs its own try/catch, and any batch that throws must be reconciled against `/jobs/applications` before reporting, because a Playwright timeout on a disabled Apply button still left three submissions behind it.
